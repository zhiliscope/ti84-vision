# TI-84 CE Python / ESP32-S3 vision terminal: feasibility

Assessed 2026-11-05. No calculator or ESP32 hardware has been accessed. “Verified” below means supported by inspected primary documentation/source, not demonstrated on the user's units.

## Decision

Proceed with a native eZ80 C calculator program acting as USB host, `usbdrvce` + `srldrvce`, and an ESP-IDF ESP32-S3 USB-OTG CDC-ACM device. This is a source-justified design, **not an established working pairing**. The first hardware milestone is framed PING/PONG with camera and Wi-Fi disabled. The complete prototype remains hardware-gated.

## Requirements and evidence

- **Native execution on OS 5.8.0.0022 — verified upstream compatibility claim; local launch unverified.** The arTIfiCE maintainer currently directs CE OS <=5.8.4 to v2.1. Current v3 is specifically for 5.8.5. Python editions are listed. Keep the existing OS for this experiment; neither an OS update nor downgrade is required. Transfer the v2.1 program and follow the maintainer's launch instructions. Source: [maintainer tutorial](https://yvantt.github.io/arTIfiCE/), [v2.1 release](https://github.com/YvanTT/arTIfiCE/releases/tag/v2.1). Stock native execution is restricted on this OS; exploit-enabled execution is a separate prerequisite from USB support.
- **Calculator USB host stack — verified implementation.** [usbdrvce](https://ce-programming.github.io/toolchain/libraries/usbdrvce.html) explicitly supports host/device operation. It is a work in progress, with timer API and isochronous limitations in the documentation. Use bulk CDC and libc `clock()` deadlines, not USB timer APIs. [Pinned source](https://github.com/CE-Programming/toolchain/tree/v15.0/src/usbdrvce).
- **Calculator CDC-ACM support — verified implementation.** [srldrvce](https://ce-programming.github.io/toolchain/libraries/srldrvce.html) provides `srl_Open`, nonblocking reads/writes, and CDC support on top of usbdrvce. Its descriptor parser searches CDC data class 0x0A for bulk IN/OUT endpoints. The header explicitly forbids `srl_Open` from an event callback; this repository defers opening to the main loop even though the upstream echo example calls it in the callback. [Header](https://github.com/CE-Programming/toolchain/blob/v15.0/src/srldrvce/srldrvce.h), [implementation](https://github.com/CE-Programming/toolchain/blob/v15.0/src/srldrvce/srldrvce.asm), [example](https://github.com/CE-Programming/toolchain/tree/v15.0/examples/library_examples/srldrvce/srl_echo).
- **TI ↔ ESP pairing — unverified.** A single CDC control interface 0 and data interface 1, one interrupt IN and two bulk endpoints, is the initial target. No claim that descriptor acceptance, class requests, reset timing, or reconnects have passed on this pairing. A custom USB class is not needed unless this CDC experiment exposes a concrete incompatibility. CH343 is not the selected device.
- **ESP USB device — verified SoC/framework support; board routing unverified.** [ESP-IDF v5.4.2 USB device guide](https://docs.espressif.com/projects/esp-idf/en/v5.4.2/esp32s3/api-reference/peripherals/usb_device.html) and [official CDC example](https://github.com/espressif/esp-idf/tree/v5.4.2/examples/peripherals/usb/device/tusb_serial_device) provide TinyUSB CDC device APIs. Native D− is GPIO19, D+ GPIO20. Use the board's native OTG Type-C connector; CH343 is UART flashing/logging. USB Serial/JTAG shares the internal PHY with USB-OTG and is not the CDC application stack. Console stays UART0.
- **Mini-USB adapter — unverified electrical role.** Marketing “OTG” and connector shape alone are insufficient. The adapter must present host/A-device ID grounding and carry VBUS, ground and data. With every device unplugged, verify Mini pin 4 ID to pin 5 GND is a low-resistance connection; verify data continuity and absence of shorts using connector drawings. Confirm host/A role in the program before connecting ESP. [USB-IF connector requirements](https://compliance.usb.org/index.asp?Format=Standard&UpdateFile=Cables+and+Connectors), [original OTG supplement, authored by USB-IF, mirrored PDF](https://www.rockbox.org/realwiki/pub/Main/DataSheets/OTG1_0a.pdf).
- **Camera/USB simultaneously — verified independent SoC facilities, unverified actual board.** [Espressif camera driver](https://github.com/espressif/esp32-camera/tree/v2.0.16) supports ESP32-S3 and OV2640 compressed output; camera uses LCD_CAM/DMA, USB uses USB-OTG. Actual camera nets must not use GPIO19/20 or memory/console/sense pins. N16R8 is a module memory suffix, not a PCB pinout. Camera compilation is disabled until a local board header explicitly acknowledges verified pins. No guessed reference pin map is selected.
- **USB power/VBUS — blocked pending board/adapter evidence.** The calculator's usable current budget for this board is unknown. No evidence establishes it can supply ESP camera/Wi-Fi peaks. Treat simultaneous PC/CH343 power and calculator VBUS as unsafe until schematic/measurements show isolation. For a self-powered design, board power must be isolated from host VBUS, ground shared, and host VBUS sensed through a suitable divider/comparator (never raw 5 V to a GPIO). TinyUSB `self_powered` and `vbus_monitor_io` implement detection, not physical isolation. See the IDF guide's self-powered section. Do not use a cable that simply removes VBUS: the device must still detect host VBUS. A powered hub is only a conditional alternative after confirming no upstream backfeed and TI hub compatibility; no purchase is assumed.
- **macOS tools — verified upstream availability.** [CEdev v15.0](https://github.com/CE-Programming/toolchain/releases/tag/v15.0) supplies ARM/Intel macOS packages. [ESP-IDF v5.4.2](https://github.com/espressif/esp-idf/tree/v5.4.2) supplies install/export and build/flash tools. Actual local compilation results are recorded separately in `evidence/VALIDATION.md`.
- **HTTPS vision — verified provider format, live operation unverified.** The optional module implements the documented [Anthropic image content format](https://platform.claude.com/docs/en/build-with-claude/vision) and [Messages API](https://platform.claude.com/docs/en/api/messages/create). Endpoint, model and API version are configurable; another provider requires a separate serializer/parser, not just another URL. No paid request is sent during development.
- **Calculator Python arbitrary USB — unverified/not selected.** TI's documented [ti_hub module context](https://education.ti.com/html/eguides/graphing/84PlusCE-TPy/EN/content/eg_pythonappprog/m_whatsnew/v5.7.0/whats_new_v5.7.0.HTML) describes its accessory ecosystem, not a general CDC host API. Do not invent `serial` or `machine.USB` APIs on the calculator. This application uses native C.

## Blocking experiments

1. Back up calculator variables; verify a CEdev hello-world launches through the OS-appropriate arTIfiCE route.
2. Identify board manufacturer/revision and obtain schematic. Check adapter ID grounding and both ports' VBUS paths while unpowered. Establish a safe supply budget or isolated self-power + host-VBUS sense arrangement before connecting calculator.
3. Flash PING-only firmware through CH343, then enumerate its native CDC port on the Mac and run host tests. This validates only the ESP ↔ Mac leg.
4. Disconnect the Mac from native USB; attach calculator only after power checks. Record host role, enabled event, `srl_Open` result and 100 PING/PONG exchanges, timeout, unplug and reconnect. Stop here on failure.
5. Only after USB passes, verify camera mapping and enable capture. Keep USB PING responsive during capture, then add Wi-Fi, TLS and a user-authorized API test.

See `HARDWARE.md`, `PROTOCOL.md` and `TESTING.md` for precise acceptance criteria and stop conditions.
